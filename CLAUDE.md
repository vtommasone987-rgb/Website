# OPTS — Asset Management & Storefront

## What this is
A web app for **OPTS (Ohio Pro Tech & Services LLC)**, an IT company, to manage physical inventory (assets, their parts, and serial numbers) and sell it through a public storefront, similar in spirit to eBay: items are listed with one or more photos, buyers browse and purchase, and a sales/analytics page reports on performance. Note: the seeded demo inventory (laptops, a camera, a drill, a server, an office chair) is placeholder data, not a reflection of what OPTS actually sells — swap it for real inventory once there's a database.

## Core features
- **Asset management (admin)**: track assets by name, model, and serial number; each asset can have multiple parts, each with its own serial number; track price, physical location, and an organizational group per asset.
- **Storefront**: public-facing listings with one or more uploaded photos per item, browsing for buyers, plus FAQ/Shipping & Returns/Contact pages.
- **Sales & analytics**: a reporting page showing sales data/metrics over time.

## Stack
- **Framework**: Next.js + TypeScript (frontend, admin pages, and API routes in one app)
- **Database**: Postgres via Prisma ORM
- **Image storage**: local disk in development; plan to move to cloud object storage (e.g. Cloudflare R2 or Vercel Blob) before production. The data model should store image URLs/keys rather than blobs, so the storage backend can be swapped without a schema change.
- **Deployment target**: Vercel (default choice; not yet deployed)

## Status
Working prototype built on top of an in-memory mock data store (`src/lib/store.ts`) instead of a real database, so the UI could be reviewed before committing to a schema:
- `/` — landing page (hero + recently-listed preview)
- `/admin` — asset list grouped by a freeform `group` label (e.g. "Reserved: Jane Doe", "Recycle"; ungrouped items get their own section), a search box + group filter that switches to a flat filtered table, an "Add a new group" form, create/edit forms (name, model, serial number, price, location, parts + their serials, storage devices, group, photo upload to `public/uploads`), delete, mark-as-sold
- **Storage devices** (`StorageDevice` in `src/lib/types.ts`) are a separate list from `Part` — a drive needs a type (HDD/SATA SSD/NVMe SSD/eMMC/Other) and a capacity in GB, which a charger or battery doesn't. Same "tracked down to the serial number" pattern as everything else: each drive has its own serial number. Shown on the storefront detail page in its own "Storage" section, same layout as "Included parts".
- Both Parts and Storage rows on the asset form start with just one row and grow via an "+ Add another part/drive" button — the only reason this needs client-side JS at all (`PartsFields.tsx`/`StorageFields.tsx`, both `"use client"`) is that adding a row without a full page reload isn't otherwise possible; everything else on this form stays a plain server-rendered field. The row `name` attributes (`part-name-0`, `storage-type-0`, etc.) are just array-index based, so `admin/actions.ts`'s parsing loop doesn't care how many rows were actually rendered — `MAX_PARTS`/`MAX_STORAGE_DEVICES` there (30/20) are just a generous server-side upper bound, not a UI limit.
- `/admin/analytics` — revenue/sales-count/average stat tiles and a recent-sales table, driven by sales recorded via mark-as-sold (moved under `/admin` since it's business data, not public)
- `/shop` — public storefront grid + `/shop/[id]` detail pages with photo gallery, description, parts, and price for available (unsold) assets
- `/faq`, `/shipping-returns`, `/contact` — customer-service pages with clearly-marked placeholder content (fake email/phone/hours, generic FAQ answers) linked from the footer; replace with OPTS's real details before going live. `/contact` also has a public support-ticket form (name, email, category — warranty/repair/feedback/other, description) that anyone can submit, no login required
- `/custom-order` — public request form for a custom PC build/laptop/tablet/other, supporting bulk requests: type, quantity, optional specific model, optional budget, details, linked right next to "Browse what's for sale" on the homepage
- `/admin/tickets` and `/admin/custom-orders` — queues for the two forms above (open items sorted first, newest first within each group), each row has a checkbox to mark it completed. The checkbox is the one place in the app with client-side JS (`(dashboard)/CompletionCheckbox.tsx`, shared by both queues) since a real checkbox needs it to auto-submit on change; everything else uses plain server-action forms
- `/admin/custom-orders/[id]` — detail page per custom order; each order has an `assetIds` list, and this page lets you attach/detach actual inventory assets to it (e.g. the specific units built or pulled from stock to fulfill the request) via an add-from-dropdown / remove-button pair
- `/admin/purchases` (+ `/new`, `/[id]`) — purchase history log for things OPTS buys for the company (supplies, tools, parts, etc.) — distinct from `Sale`, which is what OPTS sells. Tracks item, vendor, quantity, total cost, purchase date, notes, and a `group` label; list page shows total spent + count. Sits right next to Assets in the admin nav, per how it was asked for. Dates here are plain calendar dates (`YYYY-MM-DD`, from `<input type="date">`) rendered with `formatDateOnly()` in `src/lib/format.ts` rather than `formatDate()` — the latter parses via `Date` and formats in the viewer's local timezone, which shifted a date like "2026-07-01" back to "Jun 30" for anyone west of UTC. `formatDateOnly()` stays in UTC throughout so the displayed date always matches what was typed in.
- Purchases have grouping that mirrors the asset-grouping pattern exactly: an explicit "Add a new group" form (`createPurchaseGroupAction`), a group dropdown on the create/edit form, a search box + group filter that switches the list to a flat filtered table, and grouped sections (plus "Ungrouped") otherwise. Purchase groups are their own separate list (`listPurchaseGroups`/`createPurchaseGroup` in `src/lib/store.ts`) — a different domain from asset groups (e.g. "Tools"/"IT Supplies" vs. "Reserved: Jane Doe"), not shared between the two features. `PurchaseTable.tsx` and `AssetTable.tsx` are separate but structurally identical components (same `showGroupColumn` prop pattern) — worth merging into one generic table if a third grouped-list feature shows up.
- `/admin/trash` — both `Asset` and `Purchase` use soft delete: `deletedAt: string | null`. "Delete" from `/admin` or `/admin/purchases` just sets that timestamp (`deleteAsset`/`deletePurchase` in `src/lib/store.ts`) rather than removing the record, so every list/search/summary function filters `!x.deletedAt`. The Trash page lists deleted items from both with Restore (clears `deletedAt`) and "Delete forever" (`permanentlyDeleteAsset`/`permanentlyDeletePurchase` — actually splices the array; only reachable from Trash). If you land on an edit page for something deleted, it shows a short message pointing to Trash instead of the edit form.
- **Trash auto-expiry (7 days):** `TRASH_RETENTION_DAYS` in `src/lib/store.ts`. There's no background job/cron here (no server to run one on yet), so `purgeExpiredTrash()` runs as a lazy sweep inside `listDeletedAssets()`/`listDeletedPurchases()` instead — anything older than 7 days gets permanently removed whenever the Trash page is viewed, rather than on a real schedule. The Trash page shows each item's "Auto-deletes" date via `trashExpiryDate()`. Once this moves to a real deployment, pair this with (or replace it with) a Vercel Cron job hitting a route that calls the same purge function, so expiry doesn't depend on someone happening to open Trash.
- **Assigned to:** `assignedTo: string | null` on `Asset`, `Ticket`, and `CustomOrder` — optional, freeform (your name or an employee's), deliberately not on `Purchase` since that wasn't asked for. One shared name list across all three (`listAssignees()` in `src/lib/store.ts`) feeds the datalist autocomplete on every "Assigned to" field, since it's the same set of employees regardless of context. Assets set it via the create/edit form like Group/Location. Tickets and custom orders don't have an admin-editable form at creation (they're submitted publicly), so it's editable inline instead: a plain `<input>` + "Save" button per row on `/admin/tickets` and `/admin/custom-orders` (also on the custom order detail page) — `setTicketAssigneeAction`/`setCustomOrderAssigneeAction` deliberately don't redirect, just revalidate, so saving leaves you wherever you were rather than bouncing to the list page.

Branded as **OPTS** (logo mark is a placeholder single-letter "O" — swap for a real logo image whenever one exists) with "Ohio Pro Tech & Services LLC" as the full legal name in the footer copyright.

**Timezone:** `formatDate()` in `src/lib/format.ts` (used for real timestamps — ticket/custom-order submission dates, sale dates) explicitly formats in `America/New_York` rather than leaving it to whatever timezone the server process happens to run in, since OPTS is Ohio-based. Used the IANA zone name rather than a fixed "EST" offset so it automatically follows EST/EDT across daylight saving. `formatDateOnly()` (plain calendar dates, e.g. purchase dates) is intentionally left in UTC throughout instead — a bare date has no time-of-day, so there's no "Eastern version" of it, only a wrong one if timezone conversion is applied inconsistently.

`/admin` is authenticated with a username + password: `src/proxy.ts` (Next 16 renamed `middleware.ts` → `proxy.ts`) gates every `/admin/*` route except `/admin/login` behind a signed session cookie (`src/lib/session.ts`), and each mutating server action in `src/app/admin/actions.ts` re-checks the session as defense-in-depth (Next's own docs warn a proxy matcher change could silently stop covering a server action). Credentials live in `.env.local` (gitignored) as `ADMIN_USERNAME`, `ADMIN_PASSWORD`, and `ADMIN_SESSION_SECRET` — see `.env.example` for the template. The public site nav only links to Shop; admin access is a small "Seller sign in" link in the footer.

Not yet built: real database (Prisma/Postgres — deferred on purpose, see task backlog), real checkout/payment processing (mark-as-sold just records the sale internally), cloud image storage (photos currently save to `public/uploads` on local disk), and a real logo/contact details/policies (currently placeholders, see above).

**Anti-abuse:** `src/lib/rate-limit.ts` is a simple in-memory fixed-window limiter (fine while everything runs in one process on the mock store — swap the `Map` for Upstash Redis or a DB table once this is a real multi-instance deployment, so limits are shared across instances instead of reset per-instance). It's applied to: admin login (10 attempts / 15 min per IP, via `src/lib/request-ip.ts` reading `x-forwarded-for`), and the two public forms — `/contact`'s ticket form and `/custom-order` (5 submissions / 10 min per IP each). Both public forms also have a honeypot field (`name="company"`, hidden via CSS) — a bot that fills it in gets a fake success redirect with nothing actually created. None of this requires a third-party account; if spam gets past it in practice, the next step up would be Cloudflare Turnstile (needs a free account to set up).

Run locally with `npm run dev` (dev server needs Node on PATH — see below).
